# Application review — November 6, 2026

Reviewed the active WebAssembly pages, HTTP endpoints, Identity flows, household isolation, shopping/catalog/store services, offline storage and synchronization, images, barcode lookup, deployment configuration, and dependency advisories.

## Fixed

| Area | Finding | Change |
| --- | --- | --- |
| Accounts | Self-service account deletion bypassed the Users page's last-administrator and sole-household-member guards. | Both paths now use one transactional deletion service; real account-settings form tests cover rejection. |
| Login | The login page ignored `RequiresTwoFactor` and disabled failed-password lockout. | Redirect to the authenticator step with return URL/remember-me; enable Identity lockout. Both paths have real form-submission tests. |
| API validation | Null names/aliases/user fields could produce server errors; duplicate categories hit a database constraint. | Validate inputs and reject duplicate category names with useful HTTP 400 messages. |
| List quantities | Repeated adds could overflow decimals; catalog quantities below the list's minimum were accepted. | Consistent overflow handling and a minimum default quantity of 0.25. Failed adds preserve existing data. |
| Concurrency | Concurrent member removals could orphan a household; concurrent generic offer creation could create duplicates because SQLite unique indexes allow null variant keys. | Serialize these read/write operations in database transactions. |
| Membership | Adding an existing user was case-sensitive despite case-insensitive Identity usernames. | Match normalized usernames. |
| Session/privacy | Deleted users could still receive an authenticated session snapshot; private API/image responses lacked explicit cache policy. | Reject missing users, clear expired client identity, and send `Cache-Control: no-store`. |
| API UX | JSON error strings displayed with quotes, and proxy/server HTML could reach error banners. | Decode validation messages and provide readable authentication/server-error fallbacks. |
| Shared list | Server notifications had no active WebAssembly subscriber, leaving other household members' pages stale. | Refresh every 15 seconds while visible and online, plus focus/reconnect; suppress overlapping refreshes and remove listeners on disposal. |
| Offline data | Damaged queue JSON was silently treated as empty and could be overwritten. | Preserve unreadable saved data, block overwriting it, and surface a recovery message. |
| Offline UX | Queued edits were represented only by a count. | List pending actions, name rejected changes, and prevent overlapping submission of the same typed quick-add. |
| Stores/catalog | Paused stores inflated catalog availability counts; store-route changes could reuse drafts or apply stale responses. | Count active availability, reset drafts on route changes, ignore stale loads, and capture the original store ID for multi-request saves. |
| UI recovery | Several household actions threw unhandled request errors; Stores had no initial loading/empty/retry states. | Show recoverable errors and explicit states. |
| Accessibility/mobile | Image overlays did not manage modal focus; row controls were very small on touchscreens. | Use a native modal dialog, expose checked state and category-filter labels, and enlarge touch targets/input text. |

The image viewer uses the browser's modal dialog behavior to keep background content inert; see [MDN's showModal documentation](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/showModal).

## Validation

- 87 C# tests passed, up from 62 at baseline. Coverage includes actual login/account-deletion form posts, HTTP validation, concurrency, household isolation, offline retention, and active client components.
- All 6 Node test entries passed, including scanner checks, shared-list refresh lifecycle, logout cleanup, and damaged-queue preservation.
- Release publish completed successfully.
- NuGet vulnerability scan, including transitive packages, reported no known vulnerable dependencies from the configured sources.
- No database schema, Compose, volume, or environment changes are required.

## Limits and follow-up opportunities

- Rendered browser/mobile visual verification was blocked: Computer Use could not determine the Windows browser URL reliably. Modal focus and touch layout need a browser acceptance pass; compile/component checks do not substitute for that.
- Pending additions, quantity changes, and checks are now visible as saved actions, but full optimistic offline row editing remains future work. Replaying such edits needs explicit conflict semantics before synthesizing editable rows.
- Shared updates use polling, not server push. Consider push updates if household count or refresh latency warrants it.
- Large catalogs and full price-history reads would benefit from pagination and query profiling with representative data.
- Barcode-provider failures currently degrade to no match. Distinguishing provider outages from an unknown barcode would make lookup feedback clearer.
- Production verification can check the running revision/image, health, assets, and anonymous authorization boundaries. Authenticated browser acceptance requires a working browser session; local integration tests use isolated test databases.
